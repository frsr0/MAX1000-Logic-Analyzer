# MAX6675 thermocouple datalogger

The **MIL → MAX6675 thermocouple datalogger** card reads up to four MAX6675
thermocouple converters at a set interval. It saves the readings in the
backend, shows live values, graphs every enabled channel, raises alarms and
exports CSV. No FPGA change
was needed. The mock device runs the same card with simulated temperatures, so
the workflow can be tried without hardware.

## Connect the board

Tested bench wiring for two MAX6675 breakouts, each on its own three pins:

| MAX6675 breakout | Sensor 1 (measured 2026-11-16) | Sensor 2 (measured 2026-11-17) |
|---|---|---|
| SO | PMOD 1, PIO_01 (pin index 15) | D4, J1 pin 13 (pin index 4) |
| CS | PMOD 2, PIO_02 (pin index 16) | D3, J1 pin 12 (pin index 3) |
| SCK | PMOD 3, PIO_03 (pin index 17) | D2, J1 pin 11 (pin index 2) |
| VCC | 3.3 V | 3.3 V |
| GND | Common ground | Common ground |

Sensor 1's pins are the card's defaults for channel 1. For sensor 2, enable
channel 2 and set SO D4, CS D3 and SCK D2. On this bench D2 is also wired to D1
for the digital loopback tests, and the sensor reads correctly with that wire in
place.

Pin rules for the channels:

- Within a channel, the SO, CS and SCK pins must differ.
- Every enabled channel needs its own CS pin.
- A CS pin cannot be another channel's SO or SCK pin.
- SCK may be shared between channels.
- SO may be shared between channels.

The default layout enables channel 1 on SO PIO_01, CS PIO_02 and SCK PIO_03.
Channels 2 to 4 start disabled. They share that SO and SCK, with CS on PIO_04,
PIO_05 and PIO_06.

**Sharing SO between sensors is not tested on hardware.** The two tested
sensors have separate lines. A sensor whose CS is low drives the SO line. D0 to D14 have weak
pull-ups in the FPGA, but the PMOD pins do not. If several sensors share one SO
line, either put their CS lines on D0 to D14, or fit a pull-up resistor to 3.3 V
on each CS line. Separate SO lines avoid the issue.

## Use the card

1. Connect **MAX1000 OLS Logic Analyzer** on **Device** and acquire the control
   lock. Open **MIL** and scroll to the MAX6675 card, below the MCP4725 card.
2. For each channel, enable it and set its name and its SO, CS and SCK pins.
   The first channel uses the defaults above.
3. Set **Interval (s)**. The minimum is 0.5 s per enabled channel, and the
   maximum is 3600 s. The default is 1 s.
4. Optionally open **Calibration and alarms** to set an offset and alarms per
   channel (see below), and set the run options:
   - **Stop after:** no limit, 10 min, 1 h, 8 h, 24 h or 7 days.
   - **Resume after a backend restart:** on by default.
   - **Reconnect the board automatically:** on by default.
5. Choose **Read once** to check the wiring, or **Start logging** to log
   continuously. Logging can be stopped with **Stop**.
6. Use **Graph window** to show the last 1 min, 10 min, 1 h, 6 h, 24 h or all
   readings. Point at the graph to see each channel's value at that time.
7. Type a note and choose **Add note** to mark an event, such as "fan on". Notes
   show as dashed lines on the graph and in a list under it.
8. Choose **Export CSV** to download the log. **Clear** asks first, then empties
   the log, the alarm events and the notes, including the saved files.

**Units** switches the display between °C and °F. The backend always stores
°C, and the CSV is always in °C.

**Read once**, **Start logging**, **Stop**, **Clear** and **Add note** need the
control lock. The pin, calibration, alarm, interval and run-option fields are
locked while logging runs.

The stats table shows, for the graph window, the number of readings, min, max,
mean, the latest value, and the rate of change in degrees per minute over the
last 60 s.

## Calibration offset

Each channel has an offset from -20 to +20 °C, added to every valid reading.
The CSV keeps both the corrected value (`temp_c`) and the sensor's own value
(`raw_c`).

To measure an offset, put the thermocouple tip in a glass of ice and water and
stir. Wait for the reading to settle, then set the offset to minus the
reading. For example, if it reads 1.25 °C, set -1.25.

## Alarms

Each channel can have a low alarm, a high alarm, or both, from -50 to 1100 °C.
An empty field means no alarm.

- A **high** alarm starts when a reading reaches the limit. It clears when a
  reading drops more than 0.5 °C below the limit. The low alarm works the same
  way in the other direction. The 0.5 °C gap stops the alarm from flickering
  when the temperature sits on the limit.
- A **fault** alarm starts on an `open`, `bad_frame` or `error` reading, if
  **Alert on sensor fault** is ticked for that channel. It is ticked by
  default. The fault clears on the next valid reading.
- `skipped` readings do not change an alarm.

A channel in alarm gets a red outline and a HIGH, LOW or FAULT badge, and a
banner lists the active alarms. The graph draws each limit as a dashed line in
the channel's colour. **Alarm events** lists the newest changes.

**Desktop alerts** asks the browser for permission and then shows a system
notification for each new alarm. It only works while the page is open, and
only in browsers that allow page notifications. If notifications are blocked or
not supported, the card says so under the switch.

## Saved log and restarts

The backend saves the log in `data/max6675/` under the repository. It holds the
settings, the run state, every reading, the alarm events and the notes. Each
reading is written to disk as it is taken.

- **Backend restart:** if logging was running when the backend stopped, it
  starts again when the backend starts, unless **Resume after a backend
  restart** is off. The log continues from where it stopped. If the run length
  has passed in the meantime, logging does not restart, and the card says so.
- **Device disconnect:** logging keeps running and records `skipped` rows,
  with "waiting for the device to reconnect". If **Reconnect the board
  automatically** is on, the backend reconnects the board, at most once every
  10 s. It also reconnects after three sweeps in a row where every channel
  failed, for example after the USB cable is pulled and plugged back in.
- **A failed sweep** is reported as an error, and logging carries on.

The in-memory log holds the newest 200,000 rows. The graph shows those. The
CSV export reads the saved file, so it holds every reading since the last
**Clear**. The file grows by roughly 200 bytes per reading, about 17 MB a day at
a 1 s interval. Nothing deletes it except **Clear**.

## CSV columns

The file starts with a byte-order mark, so Excel shows channel names correctly.

| Column | Contents |
|---|---|
| `time_local` | Time in the backend computer's time zone, ISO 8601 with offset |
| `time_utc` | Time in UTC, ISO 8601 |
| `unix_time` | Seconds since 1970 |
| `elapsed_s` | Seconds since logging started |
| `<name> temp_c` | Reading with the offset applied, per channel |
| `<name> raw_c` | Reading from the sensor, without the offset |
| `<name> status` | `ok`, `open`, `bad_frame`, `skipped` or `error` |
| `note` | Notes, on the first reading at or after the note's time |

If two channels have the same name, their columns start with `ch1`, `ch2` and
so on.

## What the readings mean

Each reading has a resolution of 0.25 °C. The converter's range is 0 to about
1024 °C. Only room temperature has been tested.

| Status | Meaning |
|---|---|
| `ok` | A valid temperature reading. |
| `open` | The converter reports an open thermocouple. |
| `bad_frame` | The frame did not have 16 clocks, or its fixed bits were wrong. Unwired pins give this result (measured 0xFFFF). |
| `skipped` | The hardware was busy, so no read was made. |
| `error` | The read failed. The message is shown. |

A frame of all zeros reads as 0.00 °C with status `ok`. This cannot be told
apart from SO held low. **A wrong SCK pin gives exactly this result** (measured):
with SO and CS right but SCK on the wrong pin, the sensor never clocks and holds
SO low. A steady 0.00 °C at room temperature means the SCK selection is wrong.

## How a read works and why it takes 0.4 s

The signal generator drives SCK and CS. The SO line is sampled through the
generator's auxiliary input route. Each read first holds CS high for about
0.26 s. Then it clocks out the 16-bit frame at about 1 kHz. A read takes about
0.4 s per channel.

CS is held high because, on this bench, the CS pin sits low whenever the FPGA
is not driving it (measured). A MAX6675 does not start a new conversion while
CS is low, and a conversion takes up to 0.22 s. Reads without the hold returned
a stale value. With the hold, repeated reads at room temperature varied between
20.0 and 21.5 °C, as a live sensor does.

## Limits

- **Interval:** 0.5 s per enabled channel at minimum (0.5 s for one channel,
  2 s for four), up to 3600 s.
- **Storage:** see "Saved log and restarts" above.
- **Sharing the hardware:** logging pauses while a capture is armed or running,
  while the accelerometer uses the link, or while the signal generator runs.
  Paused intervals are logged as `skipped` rows, and the graph shows a gap.
  Logging resumes by itself. A capture can be started while logging. Measured:
  a capture started mid-log produced 3 to 4 skipped rows, and logging resumed.
- **Alarm state after a restart:** active alarms are not saved. After a
  restart, an alarm that is still true is recorded again as a new event.
- **Errors stay shown:** after a failed sweep or a failed reconnect, the error
  stays on the card until the next successful reconnect or the next start,
  even when readings have recovered.
- **FPGA image:** generation 4 or newer is required. Earlier images cut a
  generator capture after 50 ms, which is shorter than the 0.26 s hold. The card
  reports this if the image is older.
- **Browser:** because the log lives in the backend, reloading the page or
  opening it in another browser shows the running log.
- **Hardware tested:** one sensor on SO PIO_01, CS PIO_02 and SCK PIO_03, with
  live readings, logging through a capture, and CSV export. A second channel on
  unwired pins was logged alongside it and reported `bad_frame` throughout.
  Then two sensors (the table above) logged together at a 1 s interval: 30 rows,
  every reading `ok`, both between 20.75 and 21.75 °C side by side.
- **Tested on hardware on 2026-11-17, with the two sensors:**
  - A high alarm at 30 °C on the fan sensor (reading about 37 °C) went HIGH.
  - A -1 °C offset was applied to the room sensor, and its raw value was kept.
  - A note showed on the graph and in the CSV.
  - The °F display converted the readings and the alarm limit (30 °C showed as
    86 °F).
  - A backend restart mid-run resumed logging, with one skipped row.
  - A disconnect mid-run was reconnected automatically within about 1 s, with
    one skipped row.
  - A 60 s run length stopped the run by itself (set through the API; the card's
    shortest choice is 10 min).
  - Clear asked first, did nothing when cancelled, and emptied the log, events
    and notes when accepted.
- **Four channels (2026-11-17):** the two sensors plus two channels on unwired
  PMOD pins, at a 2 s interval, logged 15 rows in 30 s. The unwired channels
  raised FAULT alarms and the fan sensor raised HIGH.
- **40-minute run (2026-11-17):** two sensors at a 1 s interval. Results:
  - 2456 rows in 2455 s, no missing sequence numbers, every reading `ok`.
  - Interval mean 1.000 s, range 0.85 to 1.30 s, standard deviation 0.012 s.
  - No errors. The backend's memory stayed between 272 and 274 MB.
  - The saved log grew 496 KiB, about 207 bytes per row.
  - The fan sensor cycled between 30.75 and 42.0 °C about every 4 minutes. The
    room sensor stayed between 21.0 and 23.0 °C.
  - With more than 2000 readings in the window, the graph showed the min/max
    band around each line.
- **Desktop alerts:** not tested with a real notification. The app's built-in
  browser blocks notifications, and the card says so. A browser where you
  allow notifications for the page is needed.
- **Not tested on hardware:** three or four real sensors, shared SO or SCK
  lines, and runs longer than 40 minutes.
- **Hardware validation suite:** the suite drives test signals on the D and
  PMOD pins, including the pins wired to a sensor's SO output. Unplug the
  sensors before running it.

## If it does not work

- **No sensor or bad frame:** check the SO, CS and SCK selections against the
  wires, the 3.3 V supply and the common ground.
- **A steady 0.00 °C:** SO and CS are right, but SCK is on the wrong pin.
- **Open thermocouple:** check the thermocouple screw terminals.
- **Readings that never change:** check that the image is generation 4 or newer,
  and check the CS wiring.
- **Skipped:** something else is using the hardware. Stop the capture, the
  accelerometer or the signal generator. Logging resumes by itself.
